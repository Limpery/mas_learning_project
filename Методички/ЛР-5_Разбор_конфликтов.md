## 1. Постановка

До сих пор заказы добавлялись только в свободные интервалы расписания курьера. Такой план бесконфликтен, но качество его зависит от случайного порядка обработки заказов: пришедший первым занимает удобное время, пришедшему последним достаётся то, что осталось.

Между тем ресурс может **пересмотреть ранее принятое решение**. Если новый заказ выгоднее уже размещённого, имеет смысл подвинуть или вытеснить старый, а тому — поискать себе новое место. Именно эта способность отличает адаптивное планирование от инкрементального «в хвост» и составляет ядро подхода Самарской школы: решение сложной задачи ищется как результат разрешения конфликтов на виртуальном рынке.

В этой работе реализуется **простейшая форма** такого механизма: вытеснение одного, более дешёвого, заказа. Полноценный метод компенсаций — с бюджетом агента, функцией удовлетворённости и цепочками перестановок — рассматривается в курсе отдельно; о его отличиях сказано в разделе 5 этой методички.

Литература: пособие по Python (СамГТУ, 2024), глава 5; «Теоретические основы» (СамГТУ, 2023), разделы 1.3 и 2.3.

### Шаг 2. Поиск конфликтующих записей

Курьер при расчёте вариантов проверяет, не мешает ли желаемому размещению что-то уже стоящее в расписании.

```python
        jit_time_from = order.time_from - time_to_order
        jit_time_to = jit_time_from + time_to_order + time_with_order
        if jit_time_from > 0:
            conflicted_records = self.entity.get_conflicts(jit_time_from, jit_time_to)
            logging.info(f'{self} - {conflicted_records=}')
            conflicted_orders = set([rec.order for rec in conflicted_records])
```

Метод `get_conflicts` сущности курьера возвращает записи, пересекающиеся с заданным интервалом. Записи типа «Ожидание» в конфликт не входят — простой можно занять.

```python
    def get_conflicts(self, start_time: int, end_time: int) -> typing.List[ScheduleItem]:
        """Возвращает записи, пересекающиеся по времени с запрошенным интервалом"""
        result = []
        for item in self.schedule:
            if start_time <= item.start_time < end_time or \
                    (start_time < item.end_time <= end_time
                     and item.start_time != item.end_time) or \
                    item.start_time <= start_time < item.end_time or \
                    item.start_time < end_time <= item.end_time:
                if item.rec_type != 'Ожидание':
                    result.append(item)
        return result
```

### Шаг 3. Сводка по конфликтующим заказам

Одному заказу соответствует несколько записей расписания. Чтобы принимать решение, их надо свернуть до заказов: начало самой ранней записи, конец самой поздней, суммарная стоимость.

```python
            all_conflicted_records = []
            for _order in conflicted_orders:
                all_conflicted_records.extend(self.entity.get_all_order_records(_order))
            conflicted_tasks = defaultdict(dict)
            for rec in all_conflicted_records:
                task = rec.order
                min_start = rec.start_time
                max_end = rec.end_time
                max_cost = rec.cost
                if task in conflicted_tasks:
                    min_start = min(conflicted_tasks[task].get('start'), min_start)
                    max_end = max(conflicted_tasks[task].get('end'), max_end)
                    max_cost = conflicted_tasks[task].get('cost', 0) + max_cost
                conflicted_tasks[task] = {'start': min_start, 'end': max_end,
                                          'cost': max_cost}
```

### Шаг 4. Формирование варианта с вытеснением

Вытеснять имеет смысл только заказ **дешевле** нового: курьеру это выгодно. Для простоты рассматривается один, самый дешёвый, конфликтующий заказ.

```python
            poss_removing_orders = [_order for _order in conflicted_orders
                                    if _order.price < order.price]
            if not poss_removing_orders:
                logging.info(f'{self} не смог найти более дешевые заказы '
                             f'по сравнению с {order}')
                return params
            cheapest_order = min(poss_removing_orders, key=lambda x: x.price)
```

Дальше курьер считает, что получится, если он отправится за новым грузом в тот момент, когда собирался выходить за вытесняемым:

```python
            cheapest_order_records = self.entity.get_all_order_records(cheapest_order)
            # Ожидаем, что первая запись - это движение за грузом
            start_record = cheapest_order_records[0]
            start_time = start_record.start_time
            start_point = start_record.point_from
            conflicted_distance_to_order = start_point.get_distance_to_other(p1)
            conflicted_time_to_order = conflicted_distance_to_order / self.entity.velocity
            conflicted_finish = start_time + conflicted_time_to_order + time_with_order
```

Прежде чем предлагать такой вариант, надо убедиться, что он не задевает **другие** заказы:

```python
            new_conflicts = self.entity.get_conflicts(start_time, conflicted_finish)
            other_order_conflicts = [_rec for _rec in new_conflicts
                                     if _rec.order != cheapest_order]
            if other_order_conflicts:
                return params
            conflicted_price = ((conflicted_time_to_order + time_with_order)
                                * self.entity.rate)
            conflict_variant = {'courier': self.entity, 'time_from': start_time,
                                'time_to': conflicted_finish, 'price': conflicted_price,
                                'order': order, 'variant_name': 'conflict'}
            params.append(conflict_variant)
```

Теперь у агента заказа появляется третий тип варианта — `conflict`, — и он конкурирует с `asap` и `jit` по значению свёртки.

### Шаг 5. Применение варианта с вытеснением

Логику добавления заказа вынесите в отдельный метод агента курьера. Ключевой приём — **копия расписания**: если разместить заказ не удалось, состояние надо вернуть.

```python
    def add_order(self, params: dict) -> bool:
        """Добавление заказа с параметрами в расписание ресурса"""
        variant_name = params.get('variant_name')
        if variant_name == 'conflict':
            conflicted_records = self.entity.get_conflicts(params.get('time_from'),
                                                           params.get('time_to'))
            conflicted_orders = set([rec.order for rec in conflicted_records])
            if len(conflicted_orders) > 1:
                return False
            # Делаем копию расписания. Если заказ разместить не удастся, восстановим его
            old_schedule = copy.copy(self.entity.schedule)
            for rec in conflicted_records:
                self.entity.schedule.remove(rec)
            adding_result = self.entity.add_order_to_schedule(
                params.get('order'), params.get('time_from'),
                params.get('time_to'), params.get('price'), params)
            if not adding_result:
                self.entity.schedule = old_schedule
            else:
                remove_message = Message(MessageType.REMOVE_ORDER, self.entity)
                removed_order_address = self.dispatcher.reference_book.get_address(
                    conflicted_orders.pop())
                self.send(removed_order_address, remove_message)
            return adding_result

        return self.entity.add_order_to_schedule(
            params.get('order'), params.get('time_from'),
            params.get('time_to'), params.get('price'), params)
```

### Шаг 6. Реакция вытесненного заказа

Введите тип сообщения `REMOVE_ORDER`, подпишите на него агента заказа. Вытесненный заказ считает прежние оценки недействительными и начинает переговоры заново.

```python
    def handle_remove_message(self, message, sender):
        """Обработка сообщения об удалении с курьера"""
        courier = message.msg_body
        logging.info(f'{self} - удален из расписания курьера {courier}')
        self.possible_variants.clear()
        self.__send_params_request()
```

Не забудьте: **новый тип сообщения требует и объявления в перечислении, и подписки в конструкторе агента.** Забытая подписка проявится строкой «Отсутствует подписка на сообщение» в логе.

## 3. Ожидаемый результат

На конфликтном сценарии система должна прийти к плану, в котором «Доставка документов» вытесняет более дешёвый заказ и выполняется ближе к своему окну. Контрольные значения суммарной стоимости расписания: **129,45 без разбора конфликтов и 108,65 с разбором**. Если ваши значения совпали — реализация верна.

В журнале переговоров должны быть видны: обнаружение конфликтующих записей, выбор более дешёвого заказа, размещение по варианту `conflict`, сообщение вытесненному заказу и его повторные переговоры.

## 5. Чего в этой реализации ещё нет

Полезно понимать границы сделанного — из этого списка вырастают следующие работы курса:

- решение принимается по одному признаку (цена), без функции удовлетворённости агента;
- нет бюджета и **компенсаций**: вытесняемый ничего не получает за уступку, тогда как в методе компенсаций Виттиха–Скобелева уступающая сторона получает выплату, позволяющую ей найти новое место без потери удовлетворённости;
- вытеснение однократное, цепочки перестановок не строятся;
- нет критерия останова: система не проверяет, достигнуто ли конкурентное равновесие.

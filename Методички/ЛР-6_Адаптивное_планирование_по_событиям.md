## 1. Постановка

Во всех предыдущих работах план строился один раз: программа читала исходные данные, распределяла заказы и завершалась. Любое изменение мира требовало перезапуска.

В реальных системах поток событий, влияющих на план, непрерывен: приходят новые заказы, ломается техника, не выходит на работу исполнитель, сдвигаются сроки поставок. Полный пересчёт плана по каждому событию невозможен: пока считаем, приходят новые события, а построенный план успевает устареть. Об этом прямо сказано во «Введении» к «Теоретическим основам»: традиционное пакетное планирование на большой горизонт в условиях высокой динамики не даёт выигрыша.

Ответ мультиагентного подхода: **перестраивается только та часть плана, которую задело событие**. Ни один агент не пересматривает своё решение, если его ничего не коснулось. Это и есть адаптивность, ради которой всё строилось.

Для логистической задачи рассматриваются события: появление нового заказа, появление нового курьера, удаление курьера, удаление заказа.

Литература: пособие по Python (СамГТУ, 2024), глава 6; «Теоретические основы» (СамГТУ, 2023), раздел 2.3 — переходный процесс по событию.

## 2. Порядок выполнения

### Шаг 1. Удаление сущностей из системы

Расширьте диспетчер: он должен уметь находить сущность по типу и имени, отправлять её агенту `ActorExitRequest` и убирать сущность из сцены.

```python
    def remove_entity(self, entity_type: str, entity_name: str) -> bool:
        """Удаляет сущность по типу и имени"""
        entities = self.scene.get_entities_by_type(entity_type)
        for entity in entities:
            if entity.name == entity_name:
                agent_address = self.reference_book.get_address(entity)
                if not agent_address:
                    logging.error(f'Агент сущности {entity} не найден')
                    return False
                self.actor_system.tell(agent_address, ActorExitRequest())
                self.scene.entities[entity_type].remove(entity)
                return True
        return False
```

`ActorExitRequest` — служебное сообщение Thespian, а не наш `Message`, поэтому его обработку надо добавить в `receiveMessage` базового агента до проверки типа:

```python
    def receiveMessage(self, msg, sender):
        if isinstance(msg, ActorExitRequest):
            self.handle_delete_message()
            return
```

### Шаг 2. Флаг удаления и корректная выборка из сцены

Пока агент завершается, его сущность не должна попадать в новые переговоры. Введите в базовую сущность флаг `is_deleting`, устанавливайте его в обработчике удаления и учитывайте в сцене:

```python
    def get_entities_by_type(self, entity_type) -> typing.List:
        """Возвращает сущности заданного типа, которые не находятся в процессе удаления"""
        all_entities = self.entities.get(entity_type, [])
        not_deleting_entities = [entity for entity in all_entities
                                 if not entity.is_deleting]
        return not_deleting_entities
```

    while True:

### Шаг 5. Событие «появился новый ресурс»

Добавьте курьера, возящего «Срочные» заказы. Обнаружится, что ранее неразмещённый срочный заказ так и остался неразмещённым, хотя подходящий курьер появился. Причина: курьер при создании никого не оповестил о себе.

Введите тип сообщения `NEW_COURIER`. Отправка — в обработчике инициализации агента курьера, только тем заказам, которые ему подходят по типу:

```python
    def handle_init_message(self, message, sender):
        super().handle_init_message(message, sender)
        all_orders = self.scene.get_entities_by_type('ORDER')
        matched_orders = [order for order in all_orders
                          if order.order_type in self.entity.types]
        for order in matched_orders:
            order_address = self.dispatcher.reference_book.get_address(order)
            new_courier_message = Message(MessageType.NEW_COURIER, self.entity)
            self.send(order_address, new_courier_message)
```

Обработка на стороне заказа. Обратите внимание на первую проверку: **уже размещённый заказ ничего не делает** — это и есть локальность перестройки.

```python
    def handle_new_resource_message(self, message, sender):
        """Обработка сообщения о появлении нового курьера"""
        courier = message.msg_body
        logging.info(f'{self} - узнал о новом курьере {courier}')
        if not self.entity.delivery_data.get('courier'):
            self.possible_variants.clear()
            self.__send_params_request()
```

### Шаг 6. Событие «ресурс выбыл»

Удалите курьера, на которого запланированы заказы. Без дополнительной логики план не изменится, хотя исполнителя больше нет. Введите тип сообщения `DELETED_COURIER` и рассылайте его при удалении:

```python
    def handle_delete_message(self):
        super().handle_delete_message()
        all_orders = self.scene.get_entities_by_type('ORDER')
        for order in all_orders:
            order_address = self.dispatcher.reference_book.get_address(order)
            deleted_courier_message = Message(MessageType.DELETED_COURIER, self.entity)
            self.send(order_address, deleted_courier_message)
```

Заказ проверяет, касается ли его это событие, и только затем перепланируется:

```python
    def handle_delete_courier_message(self, message, sender):
        courier = message.msg_body
        if self.entity.delivery_data.get('courier') != courier:
            # Заказ не был запланирован на этом курьере, ему не надо ничего делать
            return
        self.handle_remove_message(message, sender)
```

## 3. Ожидаемый результат

Система работает непрерывно и отрабатывает три сценария:

1. **Новый заказ** — планируется автоматически, без изменения кода.
2. **Новый курьер** — ранее неразмещённые подходящие заказы находят исполнителя.
3. **Удаление курьера** — только его заказы ищут новое место, остальные не трогаются.

По каждому сценарию сохраните расписание до и после события. В отчёте отметьте, сколько агентов реально участвовало в перестройке — это количественная иллюстрация локальности адаптивного перепланирования.

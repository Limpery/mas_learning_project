## 1. Постановка задачи

Логистическая компания доставляет грузы курьерами. Каждый заказ нужно забрать в одной точке и доставить в другую, у заказа есть желаемые временны́е окна получения и доставки. Каждый курьер имеет начальное положение, скорость, ставку оплаты, грузоподъёмность, объём ранца и перечень типов грузов, которые он берётся возить.

Требуется распределить заказы по курьерам и построить для каждого курьера расписание — упорядоченный набор записей о том, куда и когда он идёт.

Решение формируется **не централизованным алгоритмом, а переговорами**: каждый заказ сам ищет себе исполнителя, каждый курьер сам оценивает, на каких условиях он готов заказ взять. Это принципиальный момент курса: мы не пишем «планировщик», мы создаём среду, в которой план возникает как результат взаимодействия.

Входные данные читаются из файла Excel, где на отдельных листах описаны заказы и курьеры.

**Лист «Заказы»:** номер, наименование, масса, объём, стоимость, координаты получения (x, y), координаты доставки (x, y), время получения, время доставки, тип заказа.

**Лист «Курьеры»:** табельный номер, ФИО, координаты начального положения (x, y), типы доставляемых заказов, стоимость выхода на работу, цена работы за единицу времени, скорость, объём ранца, грузоподъёмность.

Время всюду относительное, отсчитывается от момента t0. Расстояния евклидовы.

Литература: пособие по Python (СамГТУ, 2024), глава 3; «Теоретические основы» (СамГТУ, 2023), разделы 1.1 и 2.1.

### Шаг 3. Классы предметной области

Заведите пакет `entities`. Базовая сущность знает своё имя, идентификатор и ссылку на сцену. Поле `onto_description` — задел на будущее: позже описание сущности будет приходить из базы знаний, а пока передаётся пустым словарём.

class BaseEntity:

Класс курьера строится аналогично: `types` получается разбором строки типов через точку с запятой, `velocity`, `rate`, `max_mass`, `max_volume` — числовые характеристики, `schedule` — пустой список записей расписания.

Точка на плоскости выносится в отдельный модуль `point.py`:

```python
import math


class Point:
    """Класс точки на плоскости"""

    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __repr__(self):
        return '(' + str(self.x) + '; ' + str(self.y) + ')'

    def get_distance_to_other(self, other_point):
        return math.dist((self.x, self.y), (other_point.x, other_point.y))
```

### Шаг 5. Адресная книга и диспетчер агентов

У каждой сущности реального мира появляется представитель в мире виртуальном — агент. Связь «сущность → адрес агента» хранит адресная книга.

```python
class ReferenceBook:
    """Адресная книга агентов с привязкой к сущностям"""

    def __init__(self):
        self.agents_entities = {}

    def add_agent(self, entity, agent_address):
        self.agents_entities[entity] = agent_address

    def get_address(self, entity):
        if entity not in self.agents_entities:
            logging.error(f'Агент {entity} отсутствует в адресной книге')
            return None
        return self.agents_entities[entity]
```

Диспетчер владеет акторной системой, адресной книгой и сценой. Соответствие «тип сущности → класс агента» задаётся словарём — позже это позволит добавлять новые типы, не трогая логику диспетчера.

### Шаг 6. Протокол переговоров

Логика поиска решения раскладывается на четыре такта:

1. агент заказа запрашивает у сцены перечень курьеров;
2. агент заказа рассылает курьерам запрос возможных вариантов доставки;
3. агент курьера, исходя из своего текущего расписания, формирует варианты и отвечает;
4. агент заказа выбирает наиболее подходящий вариант и просит курьера его запланировать.

Добавьте в перечисление четыре новых типа сообщений: `PRICE_REQUEST`, `PRICE_RESPONSE`, `PLANNING_REQUEST`, `PLANNING_RESPONSE`.

Рассылка запросов агентом заказа:

```python
    def __send_params_request(self):
        all_couriers = self.scene.get_entities_by_type('COURIER')
        logging.info(f'{self} - список курьеров: {all_couriers}')
        for courier in all_couriers:
            courier_address = self.dispatcher.reference_book.get_address(courier)
            request_message = Message(MessageType.PRICE_REQUEST, self.entity)
            self.send(courier_address, request_message)
            self.unchecked_couriers.append(courier_address)
```

Расчёт варианта агентом курьера. На этом занятии вариант один — «как только смогу» (`asap`):

```python
    def __get_params(self, order: OrderEntity) -> typing.List:
        """Формирует возможные варианты размещения заказа"""
        p1 = order.point_from
        last_point: Point = self.entity.get_last_point()
        distance_to_order = last_point.get_distance_to_other(p1)
        p2 = order.point_to
        distance_with_order = p1.get_distance_to_other(p2)
        time_to_order = distance_to_order / self.entity.velocity
        time_with_order = distance_with_order / self.entity.velocity
        duration = time_to_order + time_with_order
        price = duration * self.entity.rate

        last_time = self.entity.get_last_time()
        asap_time_from = last_time
        asap_time_to = asap_time_from + duration
        asap_variant = {'courier': self.entity, 'time_from': asap_time_from,
                        'time_to': asap_time_to, 'price': price,
                        'order': order, 'variant_name': 'asap'}
        return [asap_variant]
```

Агент заказа дожидается ответа **всех** опрошенных курьеров и только затем принимает решение:

### Шаг 7. Диаграмма переговоров

Постройте диаграмму последовательности для двух заказов и двух курьеров. Ключевой фрагмент, который обязательно должен быть отражён, — **отказ**: пока первый заказ вёл переговоры, второй мог занять тот же слот, и курьер отвечает «вариант уже невыполним».

Курьер2 -> Заказ1: Параметры: время, цена
note over Заказ1 : Все курьеры ответили, оцениваем варианты
Заказ1 -> Курьер1: Прошу запланировать по варианту
Курьер1 -> Заказ1: Принято, вариант запланирован
Заказ2 -> Курьер1: Прошу запланировать по варианту
